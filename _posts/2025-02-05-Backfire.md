## Shell as ilya

Investigando en la web acerca de la aplicación "Havoc" (Que es la aplicación afectada) nos encontramos con 2 hallazgos interesantes. El primero dando prueba de que con estas configuraciones mal hechas podemos obtener un SSRF, y el segundo que se aprovecha de dicho SSRF para obtener un RCE.

### Que es un SSRF para los que no saben?

Esto no es mas que la capacidad de hacer que el servidor actué como proxy (intermediario) para nosotros como atacantes. Me explico: Al hacer una solicitud http/https por lo regular estas peticiones pasan libremente y estrictamente por el servidor, haciendo que estas peticiones cumplan con la tarea que el usuario asigno, dicho de otra forma, el usuario pide acceder al recurso `login.php`. Pues el servidor en vista de que no hay nada fuera de lo común, procede a hacer la petición sin mas. Ahora, que pasa si dicha petición no esta correctamente sanitizada, o mas bien, podemos modificar en el camino la solicitud?

De eso es que trata esta vulnerabilidad. Nosotros como atacantes le decimos en principio al servidor que como usuarios comunes hacemos una petición a X recurso, pero en medio de esa comunicación, la interceptamos y modificamos, haciendo que en vez de solicitar el recurso original, nos devuelva algo que no estaba planeado o que no esta dentro del rango de peticiones. Cosas como bases de datos, servicios internos son algunas de las cosas por las cuales podemos acceder usando al mismo servidor de intermediario.

## Port-Fowarding & Shell as sergej

Una vez obtenida la flag de user, lo que seguiría a continuación seria escalar nuestros privilegios hasta ser root. Enumerando de manera básica el sistema nos encontramos con los siguientes puertos abiertos de manera interna:

![Pasted image 20250604145839](../assets/img/writeups-img/backfire/Backfire12.png)

Tenemos algunos puertos interesantes, de entre los cuales se encuentran algunos como el 5000, el 7096, etc... Para nuestra suerte, ssh dispone de un parámetro para reenviar puertos de manera local el cual es el `-L`. Por lo que, saliendo de esta consola solamente ingresamos el mismo comando de ssh pero con el parámetro -L:

```bash
❯ ssh -L 8443:127.0.0.1:8443 -i backfire-ilya ilya@10.10.11.49
```

Ponemos el mismo puerto de ambos lados para evitar confusiones a futuro, aunque podemos dejar uno prefijo como el 80 (si no tenemos nada corriendo por allí) de la siguiente forma:

```bash
❯ sudo ssh -L 80:127.0.0.1:8443 -i backfire-ilya ilya@10.10.11.49
```

Porque usamos sudo? Porque por lo general el puerto 80 esta restringido. Entonces para evitar el uso de sudo, e ingresar siempre nuestra pass, recomiendo usar uno similar al 8000, o directamente la forma inicial.

Después de probar múltiples puertos sin respuesta, el que debemos de reenviarnos es el `7096`, ya que aquí es donde corre la aplicación que posteriormente, tiene OTRO zero-day explotable. 

Como nota extra. Si te paso igual que a mi que al ingresar vía localhost al puerto no te cargaba nada, intenta hacerlo via https `(https://127.0.0.1:<puerto seleccionado>)`, de esta manera te debería de cargar una web similar a esta:

Porque esto tiene potencial de funcionar? Tal como dice en el blog:

"Al aprovechar comentarios arbitrarios que contienen `\n` vía `iptables` y ejecutar `iptables-save`, podemos escribir archivos arbitrarios como `root`, y controlamos parcialmente sus líneas (parcialmente, sí, porque `iptables-save` genera algunos datos que no se pueden controlar) antes y después de nuestro comentario inyectado."

Entonces básicamente a raíz de esto, ssh al obtener un nuevo authorized keys (el cual nosotros mismos inyectamos) pues ignorara todo lo que no tenga formato de clave publica o parecido, aceptando la clave publica que nosotros habíamos puesto previamente.
